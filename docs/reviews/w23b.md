### Findings

1. **high**: `src/rustc_ast/tokenstream.ts:783-797` (`desugared_tts`). Upstream is `tokenstream.rs:778-787`.
   - **Cause:** `count` and `num_of_hashes` are `u8` upstream (their type is inferred from `StrRaw(u8)`), and rustc is built without overflow checks, so `count + 1` wraps to 0 after 255 while `num_of_hashes` stays at 255. The TS counts with unbounded numbers and masks only the final maximum (`num_of_hashes &= 0xff`).
   - **Failure:** for a doc comment `/// "` followed by 300 `#`, upstream produces `StrRaw(255)` and the TS produces `StrRaw(45)`.
   - **Confirmed against the oracle:** the macro `macro_rules! m { (#[doc = $s:literal]) => { const S: &str = stringify!($s); } }`, called with that doc comment, gives `S.len() == 815` on nightly-2026-10-11, i.e. 255 hashes. TS scratch run: `{"$":"StrRaw","_0":45}`. The path is reached through `rustc_expand` `parser_from_cx` → `desugar_doc_comments`.
   - The input is contrived but valid, and the `// PORT:` note claiming the final mask is equivalent is wrong.
   - **Fix:** in the `#` arm write `count = (count + 1) & 0xff`, delete the final mask, and reword the PORT note ("`u8` arithmetic wraps; rustc ships without overflow checks").
2. **med**: `src/rustc_ast/token.ts` (`LitKind_eq`, the `Err` arm, line 1577).
   - **Cause:** `a._0 === b._0` compares `ErrorGuaranteed` objects by identity. Upstream `ErrorGuaranteed(())` is a ZST with derived `PartialEq`, so any two values are equal. `ErrorGuaranteed.unchecked_error_guaranteed()` returns a fresh object each time.
   - **Failure:** two `Literal(Lit { kind: Err(_), .. })` tokens with the same symbol and suffix compare unequal in `TokenKind_eq` / `Token_eq` / `TokenTree.eq_unspanned`, where upstream says equal. That is latent until macro matching or `eq_unspanned` users are ported.
   - **Fix:** make the arm `return b.$ === "Err";`, and add `ErrorGuaranteed` to the "ZST, always equal" list that codegen and hand-written `_eq` helpers follow. Grep for other `_eq` helpers that compare `ErrorGuaranteed` fields.
3. **med (process)**: no committed test or difftest exercises `util/literal.ts` (`from_token_lit`, `LitKind` Display), `Token.glue`, `break_two_token_op` or `TokenCursor`.
   - The handoff's "runtime smoke" was not committed, and the `lex` suite does not reach these functions.
   - **Fix:** commit the smoke checks as `bun:test` cases with expectations taken from the oracle: `0b102` → `IntTooLarge(2)`, `1f32` → `Float(Suffixed(F32))`, `1u7` → `InvalidIntSuffix`, escapes in str/byte-str/c-str, raw strings, glue pairs, and `desugared_tts` with 0/1/3/256+ hashes. Better still, add an oracle probe for literal cooking (a harness batch).
4. **low**: `tokenstream.ts:347, 523, 527, 559, 561, 856-858`. The code uses spread arguments (`push(...xs)`, `splice(start, len, ...replacement)`). Upstream `extend`/`splice` have no size limit, but bun throws `RangeError` at around 600k+ elements.
   - **Fix:** use a loop push, or a shared `extend` helper in `src/std`.
5. **low**: `tokenstream.ts:514-519`. `attrs.partition_point(..)` is replaced by a linear scan.
   - The PORT note is honest, but the replacement is correct only for partitioned input, and nothing checks that.
   - **Fix:** move the faithful `partition_point` from `src/rustc_span/source_map.ts:1463` into `src/std` and use it here.
6. **low**: `util/parser.ts:170`. `ExprPrecedence_discriminant` is hand-written.
   - The values are correct (they follow variant order), but `derive(PartialOrd)` on a fieldless enum is exactly what `tools/codegen/types.ts` should emit as `<E>_discriminant` (wave-1 cross-lane item).
   - **Fix:** have codegen emit it for every `PartialOrd`/`Ord` fieldless enum, then delete the hand copy.
7. **low**: `MetaItemLit.from_token_lit/from_token/as_token_lit` exist only after `util/literal.ts` has been imported for its side effects.
   - **Fix:** root should add `import "./util/literal.ts"` to `rustc_ast/lib.ts`, as the handoff asks. Until then, calling them before that import is a `TypeError`, not an `unported`.

### Findings

1. **med**: `src/rustc_errors/diagnostic.ts:1287-1300` (`Diag.drop`) and `lib.ts:997` (`DiagCtxtInner.drop`).
   - **Cause:** the drop bomb and the context drop run only when called explicitly. The PORT note and the handoff say so.
   - **Failure:** a ported caller drops a `PResult` error without `.emit()`/`.cancel()`. Upstream prints "the following error was constructed but not emitted" plus the diagnostic, then ICEs (exit 101). TS prints nothing and exits normally. Porting bugs of exactly this kind stay hidden from difftest unless the expected output happens to contain the dropped error.
   - **Fix:**
     - Keep a registry of live `Diag`s on `DiagCtxtInner`: add in `Diag.new_diagnostic`, remove wherever `diag` becomes `undefined`.
     - `DiagCtxtInner.drop()` and the driver/test teardown call `.drop()` on survivors, in creation order.
     - Root must also wire `dcx.inner.drop()` into the driver exactly where upstream drops the session.
2. **med**: `src/rustc_errors/lib.ts:122-125` (`LintExpectationId` stand-in), `Level_eq` (`lib.ts:1543`), and `fulfilled_expectations: Set<LintExpectationId>`.
   - **Cause:** the stand-in is an opaque object compared by identity. Upstream `LintExpectationId` has derived `PartialEq`/`Hash` and lives in an `FxIndexSet`.
   - **Failure:** once rustc_lint_defs is ported, two equal ids built separately would both be inserted, and `contains` on an equal id would be false. That would break `unfulfilled_lint_expectations` and `Level_eq` on `Expected`/`Forced` levels.
   - **Fix:** record this in the rustc_lint_defs lane brief. `LintExpectationId` must become an interned handle or carry a canonical string key, and the set and `Level_eq` must compare by value.
3. **med (process)**: `src/rustc_errors/lock.ts:13-15`. The three `cfg(windows)` functions of lock.rs are `rustc-skip`. That is outside PORTING §3's allowed skip kinds, and no decision is recorded.
   - The substance is fine: the target is non-windows and the non-windows no-op is ported.
   - **Fix:** root runs `state.ts record decision` to ratify it, together with the other platform-cfg skips.
4. **low**: `src/rustc_error_messages/diagnostic_impls.ts:151-156`. `Backtrace.capture()` calls `unported` when `RUST_LIB_BACKTRACE`/`RUST_BACKTRACE` enable backtraces.
   - The `unported` is honest, but any run with `RUST_BACKTRACE=1` that records a delayed bug or calls `set_must_produce_diag` becomes UNPORTED (exit 70), even when the delayed bug is later discarded and the output would be ordinary.
   - **Fix:** return `new Backtrace("Captured")` and keep `unported` only in `to_string()`, the only place frames are observable. Then move the shim to `src/std` (handoff request).
5. **low**: `src/rustc_errors/diagnostic.ts:1254-1256` (`cancel_into_message`).
   - Upstream's `?` early returns drop `self`, so a `Diag` whose `diag` is `Some` but has no messages fires the bomb. TS returns `undefined` and leaves the `Diag` live. This is hard to reach (`DiagInner::new` always has one message).
   - **Fix:** call `this.drop()` before the second `return undefined`.
6. **low**: these assert messages are abbreviated or guessed:
   - `rustc_errors/lib.ts` `emit_diagnostic`: `assert_matches!` uses the made-up text `"assertion failed: assert_matches!(..)"`.
   - Every `assert_eq!` in `lib.ts` (delayed-bug clear, `panic_if_treat_err_as_bug`, the steal functions) and in `diagnostic.ts:1198,1207` prints only the first line.
   - Upstream's format (core/src/panicking.rs:434) is `` assertion `left == right` failed\n  left: {:?}\n right: {:?} ``, and for `assert_matches!` it is `` assertion `left matches right` failed\n  left: {:?}\n right: Error | Warning(_) ``. These texts appear only in ICE output.
   - **Fix:** add `assert_eq(left, right, debug)` / `assert_matches` helpers to `src/std/panic.ts` (root-owned) that produce the exact text, and use them.
7. **low**: `rustc_errors/lib.ts` and `diagnostic.ts` (`panicking()`). The function always returns `false`.
