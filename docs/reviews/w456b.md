## 1. emitter: ACCEPT-WITH-FIXES

**E1. MEDIUM, confirmed.** `src/vendor/termize/platform/unix.ts:38` (`ioctl_tiocgwinsz`) vs termize-0.2.1
`src/platform/unix.rs` (`ioctl(fd, TIOCGWINSZ)`).
- **Cause.** The function runs `new WriteStream(fd).getWindowSize()` and never destroys the stream. Bun's tty
  `WriteStream` opens a new fd each time.
- **Why it matters.** `AnnotateSnippetEmitter` calls `termize::dimensions()` for each diagnostic when neither
  `diagnostic_width` nor `ui_testing` is set (annotate_snippet_emitter_writer.ts:518, upstream order). So every
  diagnostic emitted while stdout, stdin or stderr is a TTY leaks one fd.
- **Scenario.**
  - Under a pty, 3000 `dimensions()` calls took the open fd count from 5 to 3005.
  - With `ulimit -n 256` (the macOS shell default), a later `openSync` fails with EMFILE.
  - So an interactive run that prints about 250 diagnostics would crash on its next file read.
  - Upstream's ioctl opens nothing.
  - The harness is unaffected, because no stream is a TTY there.
- **Fix.** `const ws = new WriteStream(fd); try { ... ws.getWindowSize() ... } finally { ws.destroy(); }`.
  - Do not cache one stream per fd: Bun caches the size, so resizes would be missed.
  - Check that the `/dev/tty` branch, which opens its own fd, does not close it twice.
  - Tested in scratch `fix2.ts`: fds stay at 7, a resize from 77×22 to 50×9 is seen, and stderr stays writable.

**E2. MEDIUM, unconfirmed (host is macOS).** `cfg!(windows)` is hard-coded false in three vendor files, but
emitter.ts:611 checks `process.platform`:
- anstream `auto.ts:19`
- anstyle_query `lib.ts:55-90`
- termize `platform/mod.ts`

On a Windows console the colour decision (`Auto`, TERM unset) and the width (stdout redirected) would differ from
rustc. Fix either way:
- select the `cfg(windows)` arms at runtime, consistent with emitter.ts; or
- root records the decision "Windows TTY behaviour out of scope; vendor stack assumes non-Windows".
