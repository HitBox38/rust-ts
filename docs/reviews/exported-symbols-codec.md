## Byte-level fidelity (checked against upstream; all OK)

- `rustc_macros/src/serialize.rs` `encodable_body`: an enum with more than one variant emits `emit_u8(disc)` because
  it has fewer than `u8::MAX` variants. A fieldless enum emits only the discriminant. A struct emits its fields in
  declaration order. `decodable_body`: `read_u8() as usize`, then the panic text
  ``invalid enum variant tag while decoding `{}`, expected 0..{}, actual {}``. All of these are reproduced
  (`exported_symbols.ts:170-181`).
- Variant order and indices match `exported_symbols.rs`:
  - `SymbolExportLevel` C=0, Rust=1.
  - `SymbolExportKind` Text=0, Data=1, Tls=2.
  - `ExportedSymbol`: NonGeneric=0, Generic=1, DropGlue=2, AsyncDropGlueCtorShim=3, AsyncDropGlue=4,
    ThreadLocalShim=5, NoDefId=6.
- `SymbolExportInfo` field order matches upstream: `level`, `kind`, `used`, `rustc_std_internal_symbol`. Both bools
  go through `emit_bool` / `read_bool`.
- Field encoders are the ones upstream reaches through a TyEncoder / TyDecoder:
  - `DefId` uses `SpanEncoder::encode_def_id` (`rustc_span/lib.ts:1820`).
  - `GenericArgsRef` is encoded as a `&List` (len, then the elements), via `encode_RawList`.
  - `Ty` uses `encode_with_shorthand` / `decode_Ty`, with shorthand handling (`ty/codec.ts:316`, `:383`).
  - `SymbolName` encodes its `&str` field (BindStyle::Move) with `emit_str`. Its decode is the manual
    `codec.rs:276` impl (`decode_SymbolName`, `SymbolName::new(interner, read_str())`).
- Decode keeps upstream's order of field reads (`_0` is bound before `_1` in Generic and AsyncDropGlue).
- Tuple codec: upstream `(A, B)` encodes and decodes its elements in order. `encode_tuple` / `decode_tuple_` are
  used at `encoder.ts:2891` and `decoder.ts:1799`. Upstream `encode_exported_symbols` (encoder.rs:2394) is
  `lazy_array(exported_symbols.iter().cloned())`, which matches `encoder.ts:1919`.

## Findings

1. **blocking**: `src/rustc_middle/middle/exported_symbols.ts:40,55,81,107,136` and `src/rustc_middle/ty/mod.ts:2932`.
   The derived `TyEncodable`/`TyDecodable` (SymbolExportLevel, SymbolExportInfo, ExportedSymbol), `Encodable`/
   `Decodable` (SymbolExportKind) and `TyEncodable` (SymbolName) are hand-written.
   - Rules: PORTING §3 says these derives "are generated by `tools/codegen` ..., not hand-written". PORTING §5 says
     "do not hand-write them". plan-m5 D3 says the derive sites "are generated".
   - Codegen can handle these types. The `rustc_middle` set in `tools/codegen/types.sets.json` already parses
     `ty/mod.rs`, has `derive_encodable`/`derive_decodable` on, and limits output to a `decodable_types` whitelist.
     `serialize.json` already has entries for every field type: DefId, `GenericArgsRef`, `Ty`.
   - Precedent: a hand-written exception needs a recorded root decision (e.g. small-gaps-19 for CapturedPlace,
     where the probe could not parse `closure.rs`). No such decision exists for this batch.
   - Remedy, either:
     - (a) Add `compiler/rustc_middle/src/middle/exported_symbols.rs` to the `rustc_middle` set's `files`, add the
       four types and `rustc_middle::ty::SymbolName` to `decodable_types`, then regenerate. SymbolName gets only the
       derived encode; its manual decode stays in codec.ts. Then import from `decodable.gen.ts`.
     - (b) If codegen really cannot do this, record a root decision saying why, and mark each fn with the repo's
       hand-derive marker (next finding).
   - Either way the bytes should not change.
2. **non-blocking** (moot under remedy (a)): `exported_symbols.ts:40-159`, `ty/mod.ts:2932`. The hand-written derive
   fns carry only `// PORT:` prose. The repo's convention for hand-written derives is a
   `// rustc-derive: <path>:<line> <Trait> for <Type>` marker above each fn: `rustc_target/asm/mod.ts:150-160`,
   `ty/closure.ts:273`, `ty/mod.ts:1388`, and the same format that `tools/codegen` emits.
3. **non-blocking**: `exported_symbols.ts:155`. `default:` decodes tag 6 as `NoDefId`. This is correct only because
   `decode_variant_index` has already rejected `tag >= 7`. `case 6:` would mirror the derive's `6 => ...`
   arm literally.
4. **non-blocking**: `exported_symbols.ts:2-4`. The header still says the derived codecs "are the metadata codec's
   (rmeta encoder/decoder lanes)". That is stale now that they live in this file.
5. **non-blocking**: `exported_symbols.ts:170-181` duplicates `encode_fieldless_enum`/`decode_fieldless_enum` from
   `rustc_target/asm/mod.ts:174-191`, minus the 0-variant, 1-variant and ≥255-variant branches. That is fine for
   these types, and the doc comment says so.

    `cstore_impl` and codegen_ssa.
