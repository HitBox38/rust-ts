## What was checked, and how
1. **Markers / order / names.** A script (`/tmp/pmrev/markers.ts`) lists every `fn` in the 5 upstream files and
   checks each `// std: library/proc_macro/src/<f>.rs:<line> <name>` in src/proc_macro. Result: 189/189 upstream
   fns covered (lib 111, diagnostic 16, escape 3, to_tokens 37, quote 22). No marker points at a line with no fn of
   that name, and there are no duplicates. Fns generated by macros (`suffixed_int_literals!`, `integer_values!`,
   `float_values!`, `diagnostic_child_methods!`, `diagnostic_method!`) are expanded by hand with a comment naming
   the macro, as other lanes do. The six places where markers run backwards are later `impl` blocks folded into the
   class body (FromIterator/Extend/IntoIterator into `TokenStream`, `PartialEq<char>` into `Punct`, `Iterator for
   Children`), with the `Debug` impls placed after the class (PORTING §8). I read every ported body against
   upstream: TokenStream and the two Concat helpers, IntoIter, Span, TokenTree, Group, Punct, Ident, Literal (all
   constructors, `with_stringify_parts`, the `*_value` fns, `parse_number`, `strip_underscores`, `from_str`, Display
   and Debug, including the `PLAIN` one-line kind/suffix in `Debug for Literal`), `tracked`, the 23 EscapeError
   Display strings (diffed mechanically: identical), and all of diagnostic.rs, escape.rs and to_tokens.rs. I found
   no logic divergence.
2. **`minimal_quote!` template.** Rust expands `minimal_quote!` into one `ToTokens::to_tokens(&minimal_quote_ts!($t),
   &mut ts);` per tt, left to right. A group's contents are built first, then `Group::new` runs. `(@ e)` evaluates
   `e` at its place in that sequence. `minimal_quote_toks` / `minimal_quote_ts` / `minimal_quote_tt` do the same,
   with each hole as a thunk, so they make the same server calls in the same order:
   - `span_save_span` inside `quote_span`, reached through the `(@ quote_span(..))` holes;
   - `literal_from_str` for the `$lit:literal` arm, e.g. `0usize`;
   - `ts_concat_trees` / `ts_into_trees` for each `to_tokens`.

   The arm order matches upstream: groups, the single-char puncts, `_`, ident, literal, plus the four
   `minimal_quote_ts!` operator arms. In `quote()` itself the evaluation order also matches upstream:
   - the Ident arm builds `ctor` before the template;
   - the repetition arm reads `iter.next()` before `iter.peek()`;
   - `collect_meta_vars(contents.clone())` runs before the setup template.

   The template reader rejects other glued operators and stray `@`, so a future template that needs an arm the macro
   doesn't have fails loudly instead of being silently re-tokenised. This approach is faithful under PORTING's
   rules: the macro text is kept verbatim and expanded by the macro's own arms. The unit test checks span-save order
   ("one span per quoted ident/literal, in token order"), and the end-to-end oracle match below depends on it,
   because the `recover_proc_macro_span(N)` ids are visible in expanded output.
3. **Contract block vs pm-bridge in `integ-w35`** (`c2e7e541`). Every declared item exists with the same name, the
   same parameter/return types and the same semantics:
   - client.ts: `TokenStream` (`handle`, `clone()` → `Methods.ts_clone`), `Span.{def_site, call_site, mixed_site}`,
     `debug_Span` (→ `span_debug`), `is_available`, and `Methods`, all 31 `with_api!` methods in the same order with
     identical signatures;
   - symbol.ts, re-exported by client.ts: `Symbol.{new, new_ident, with}`, `debug_Symbol`, `display_Symbol`.

   `Methods`, `Span` and `Symbol` are plain unfrozen objects, so quote.test.ts's `Object.assign` mock works on them.
   The brand strings differ (`…::client::Symbol` in the contract vs `…::symbol::Symbol` in pm-bridge), but that
   disappears with the block. I checked this with a trial merge (`git merge --no-commit` of 2945d0af into
   integ-w35, in a scratch worktree that was discarded afterwards). It merged with no conflicts; lib.ts and
   diagnostic.ts are unchanged between b0008692 and integ-w35. I then replaced the block with an
   import/re-export from `./bridge/client.ts` and added `export type ClientMethods = typeof BridgeMethods`. Result:
   `tsc` clean, `bun test src/proc_macro src/rustc_expand` 274 pass / 0 fail, so the mock also works against
   pm-bridge's real objects. Mismatches are listed as N1 and N2.
4. **Test provenance.**
   - escape.test.ts: I recompiled the lane's probe (it `#[path]`-includes upstream escape.rs verbatim) with
     `rustc +nightly-2026-10-11`, printed the raw strings, and compared them with `CASES`: 24/24 identical.
   - quote_oracle/expected.json: for each of the 7 inputs I ran the oracle's `-Zunpretty=expanded` on
     `proc_macro::quote! { <input> }` myself, applied the normalisation described in the test header, and got 7/7
     identical to `expected`.
   - The remaining quote.test.ts literals follow from upstream: the panic texts are quote.rs's, and the
     `Punct::new` message is `{:?}` of the char. The ToTokens and constructor strings are Rust's Display of those
     values. Nothing is taken from TS output.
5. **`unported` left.** These are genuine gaps in src/std, and the messages name them accurately.
   - `f16_value`: there is no f16 anywhere in src/std.
   - `f32_value`: src/std has no correctly rounded `f32::from_str`. `Math.fround(Number(s))` would round twice.
     `rustc_apfloat`'s `from_str_r` exists, but it implements LLVM's grammar, not core's dec2flt.
   - `<f32 as Display>`: fmt.ts has `F32_SPEC` and a private `to_shortest_str`, but exports only `debug_f32`. The
     std follow-up in the handoff is correct.
   - The other `unported` calls are the `(pending pm-bridge)` contract stubs, removed at merge.

## Findings
- **N1 (non-blocking, merge wiring; contract mismatch).** `src/proc_macro/bridge/client.ts` (integ-w35) types
  `Client.expand1(f: (input: CrateTokenStream) => CrateTokenStream)`, where `CrateTokenStream` is the structural
  `{ _0 }`. pm-lib's `quote(stream: TokenStream): TokenStream` (quote.ts:542) takes the full class, so merge step 3,
  `Client.expand1(quote)`, fails with TS2345 ("CrateTokenStream is missing … clone, is_empty, …"). At run time it is
  sound: every value reaching `quote` is built by `crate_TokenStream.new_`, i.e. it is a `TokenStream`. The fix
  belongs to root at merge: either cast at the call site, or type `crate_TokenStream.new_` / `CrateTokenStream` as
  lib.ts's `TokenStream` (for example, client.ts imports the type only). Neither handoff mentions it.
- **N2 (non-blocking, handoff accuracy).** Merge step 1 says "import the same items" from `./bridge/client.ts`.
  diagnostic.ts (`BridgeMethods`, `client_Span`) and quote.test.ts (`BridgeMethods`, `ClientMethods`,
  `client_Span`, `client_Symbol`, `client_TokenStream`) import them from `./lib.ts`, so lib.ts must **re-export**
  them, and `ClientMethods` must become `export type ClientMethods = typeof BridgeMethods`. Otherwise those two
  files break. The handoff's step 4 (the mock may need pm-bridge's own test hook) turned out to be unnecessary: the
  mock works as-is.
- **N3 (non-blocking, stale header).** lib.ts:27-28 says bridge/server.ts "attaches `Client::run1` / `Client::run2`
  to bridge/client.ts's class". In integ-w35 they are part of client.ts's `Client`, and the lib.ts header still
  calls them pending. pm-bridge's handoff (Integration step 4) lists this. Root should refresh it at merge.
- **N4 (non-blocking, order).** Two `std-type` declarations are out of upstream order:
  - `Delimiter` (lib.rs:913) comes after `Group`'s Display and Debug (lib.rs:1025/1032), at lib.ts ~1045.
  - `Children` (diagnostic.rs:84) comes after `impl Diagnostic` (diagnostic.ts ~226).

  Neither move is needed: `Children` is only referenced at call time. Fn markers are in order apart from the folded
  impls noted above.
- **N5 (non-blocking, names).** `Diagnostic`'s fields are `level_` / `message_` / `spans_` / `children_`
  (diagnostic.ts:52-57) because the getters take the Rust names. PORTING §4 says fields keep their name. A
  `// PORT:` line on the constructor would record the reason, and `debug_Diagnostic` already prints the Rust field
  names.
- **N6 (non-blocking, harness follow-up).** As the handoff says, `coverage.ts --missing` reports `0/N` for
  `library/proc_macro/src/*` because it counts only `// rustc:` markers. `--check` therefore does not validate
  `// std:` lines either. The marker script above covers this batch; a harness lane should teach coverage.ts about
  `// std:` for `library/` paths.

## Contract mismatches (summary for root)
Names, signatures and semantics of every contract item match pm-bridge. The only type-level mismatch is N1
(`Client.expand1` vs `quote`'s parameter type); the wiring caveat is N2 (re-export, not just import).
