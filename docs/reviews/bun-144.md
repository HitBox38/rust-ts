## Findings

**F1. A Bun change during a gate goes undetected. gate.json `bun` then names a build the run's children did not use, and
`accept` passes the run.**

Where: `scripts/gate.ts:611` reads the build once, from the gate process itself (`runningBun()`, `scripts/lib/bun-pin.ts:21`).
The final write records that same value (`scripts/gate.ts:731`).

The gate process keeps the build it was started with. But every child it starts is spawned as `process.execPath`, the *path*
`~/.bun/bin/bun`. Those children are:
- the static steps (`scripts/gate.ts:411`, 567–573);
- the oracle runners of the 20 Bun-run suites, for example `harness/suites.ts:2114`, 2170 and 2282;
- source-mode subjects (`scripts/lib/subject-bin.ts:688`);
- the builder (`scripts/lib/subject-bin.ts:661`).

Each of them runs whatever file is at that path at the moment it starts. Binary-mode subjects are immune, since their runtime is
embedded; the others are not.

Evidence. I copied 1.4.3 to a scratch path, started a script with it, and swapped the file for 1.4.4 with `cp` + `mv` (an atomic
replace, as an upgrade does). The script printed:

```
start: self 1.4.3, child 1.4.3+c6da4a4d3, file 869d5d72838f
end:   self 1.4.3, child 1.4.4+38afee6c8, file 7c1f29cd4051
```

So `Bun.version`/`Bun.revision`, which is what gate.json records, still says the old build while the children run the new one.

There is a second problem: `difftest.ts` `oracleVersion` caches the hash of `process.execPath` once per suite
(`scripts/difftest.ts:287`). A swap in the middle of a suite therefore stores runner output from the new Bun under the old Bun's
key, which poisons the oracle cache beyond this run.

On 2026-11-11 this happened during the gate's last suite (w40j-audit N1). It was found only by a manual audit of
`~/.bun/bin`'s timestamps, and the file's own mtime does not show it: `~/.bun/bin/bun` has mtime Oct 22. So detection must use
the content.

Fix, about 10 lines plus a test:
1. At the start, read the build behind `process.execPath` (`Bun.spawnSync([process.execPath, "--revision"])`, or a sha1 of the
   file, about 0.1 s for 88 MB). Require it to equal `runningBun()`.
2. Read it again before each suite and at the end.
3. On a change, print one `ERROR:` line, stop or fail the run (`pass: false`), and record `bunEnd`, or the suite at which the
   change was seen, in gate.json.
4. For defence in depth, let `accept` refuse a gate.json whose `bunEnd` differs from `bun`.

Test it through a `GateHost` override for the end-of-run reading, as `GateHost.bun` does for the start.

## Nits

**N1. "Before anything else" is not enforced by the tests.** Moving the Bun check after the suite-name and env checks
(`scripts/gate.ts:614-616`) passes all 7 tests. Both checks are side-effect-free, so this is harmless today. Either add a test
case that gives an unknown suite *and* another Bun and expects the Bun `ERROR:` (`scripts/gate-bun.test.ts:85`), or soften
"before anything else" in `scripts/gate.ts:32` and `scripts/lib/bun-pin.ts:4` to "before any work".

**N2. The static-stop write's `bun` is untested.** No test reads `bun` from the gate.json written at `scripts/gate.ts:667`.
`scripts/gate-static-stop.test.ts:71` checks the other fields of that file. Such a run can never be accepted, so this is only
informational; one assertion would close it.

**N3. Validating the next Bun will fail the runner step until `GATE_BUN` changes.** On 1.4.3 (any non-pin build),
`scripts/gate-power.test.ts`, `scripts/gate-static-stop.test.ts` and `scripts/gate-probes.test.ts` give 18 failures and 4
passes. Every failure is the pin's `ERROR:`, because these tests drive `gateRun` on the running Bun. `scripts/lib/bun-pin.ts:7-9`
says to validate and re-check the candidate *before* changing `GATE_BUN`, but the runner tests cannot pass on the candidate in
that order. Either pass `bun: GATE_BUN` through `GateHost` in those tests (they test other things), or state in the procedure
that the runner step is run after the `GATE_BUN` change, in the same batch.

**N4 (for root, not the lane).** The first gate after the merge re-runs the oracles of the 20 suites. Among them are the
protected split runs rmeta-core (82,338 protected), rmeta-std, rmeta-alloc, check-core/std/alloc/rg/rg-encode-mir and the
miri-sysroot ones, and no review has sampled those on 1.4.4. If a Bun-run runner's output changed with 1.4.4, it shows up as
protected losses during the ~10 h gate. A one-off `difftest` of those single-key suites before the gate would find out cheaply.
AGENTS.md §2 could also name `scripts/lib/bun-pin.ts` next to the battery rule, as the lane suggests.
