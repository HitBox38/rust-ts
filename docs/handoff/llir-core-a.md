## The contract's shape (for llir-core-b and the fill lanes)

- **Ported code imports only `src/rust_ts/llvm/ffi.ts`**, as `llvm::ffi`. It re-exports the enums (`Linkage`, …,
  `Linkage_discriminant`), `Bool`/`TRUE`/`FALSE`/`to_llvm_bool`, `RawEnum`, `MutRef`, `RustString`, and the handle types.
- **Signatures** keep ffi.rs's parameters one for one, so a call reads like the Rust one:
  - a pointer and length stay two arguments: `LLVMFunctionType(ret, params, params.length, FALSE)`;
  - a PTR_LEN_STR is `PtrLenStr`: a JS string stands for its UTF-8 bytes, a `Uint8Array` is raw bytes;
  - a `*const c_char` is `string`;
  - **every raw pointer is `| undefined`**: port `ptr::null()` as `undefined`, and a null array with length 0 as `[]`;
  - 64-bit integers are `bigint`; `size_t`, `usize` and `c_uint` are `number`;
  - out-parameters are `MutRef<T>`, `Option<&T>` is `T | undefined`, and C callbacks are `unknown`.
- **Handles are opaque to ported code.** Compare them with `===`: the model uniques types, constants and attributes per
  context, as LLVM does. A returned name is decoded from UTF-8; inside the model, names are byte strings (`bstr`).
- **Adding an implementation**: export a function of the ffi name from a module listed in `src/rust_ts/llvm/impl_modules.ts`
  (`./core.ts` today; llir-core-b adds e.g. `./build.ts`), then run `bun tools/llir/ffi_gen.ts`. tsc checks the function against
  the contract's signature, and `ffi.test.ts` fails until the file is regenerated.
- **Extension points for llir-core-b**, in `ir.ts` and `printer.ts`:
  - `Instruction` (abstract, extends `User`: operands, `setOperand`, users for RAUW) and `BasicBlockBase`.
  - `Function.blocks`, `.personality`, `.symTab`. Locals share the function's one collision counter.
  - `setBodyPrinter`, `Printer.localOperand`, and `Printer.operand`/`constant`/`type`.
  - `handles.ts`: replace the brands with your classes.
  - Add types used only in bodies to the printer's type finder.
  - Stops left for you: `stripPointerCasts` through instructions, `LLVMSet/GetAlignment` on instructions,
    `LLVMDeleteFunction` of a definition, printing bodies and unnamed locals.
- **Port-side trace**: `bind` writes `scripts/lib/llvm-trace.ts`'s format, including the `LLVMBuild*` answers
  (`inst`/`operand`/`const …`). It assumes instructions extend `Instruction`.

## The recorder: what it records

`bun src/rust_ts/llvm/record.ts <out.script> -- <rustc argv>` loads a dylib through `DYLD_INSERT_LIBRARIES` into the
toolchain's own `bin/rustc`. The dylib is built with `cc` and cached in `$RUST_TS_DATA/llvm-record/<hash>/`. It has one wrapper
per ffi.rs C function that librustc_driver imports, typed from ffi.rs. Each wrapper logs handles, integers, doubles, byte
strings, arrays, returned strings and out-parameters. **The oracle's IR is byte-identical under the recorder** (the proof test
checks every case).

The 131 `LLVMRust*` wrappers are never seen. Their effects are observed from C-API-readable state instead, as inferred lines:
`?global`, `?function`, `?datalayout`, `?triple`, `?flag`, `?attr`, `?attrs`, `?dsolocal` (the full list is in `record.ts`'s
header). Replay attributes each to its rustc producer (F1 above).

Two C API traps found on the way, which the recorder avoids:

- `LLVMCopyModuleFlagsMetadata` hits `llvm_unreachable` (a trap in the release build) on the **Max and Min** behaviours, which
  rustc's `PIE Level` and `PIC Level` use. The recorder reads the flags through the named metadata's node operands instead.
- `LLVMGetStructName` returns a borrowed string; freeing it aborts.

### What a replay cannot catch (for the fill lanes)

1. Any `LLVMRust*` call whose effect the C API cannot read: call-site attributes (`LLVMRustAddCallSiteAttributes`), the builder
   wrappers (`LLVMRustBuildMemCpy`, …, `LLVMRustPositionBuilder*`), debuginfo wrappers, inline asm, and changes to existing
   values beyond those listed in F1.
2. Which wrapper made an inferred effect, where two rustc producers make the same one. Replay picks by the tables in
   `replay.ts`: for example `GetOrInsertGlobal` versus `…InAddrspace` in the default address space, or a literal flag site
   versus `-Z llvm-module-flag`.
3. The order of inferred effects within one gap between recorded calls, and rustc's grouping and order of attributes (the C API
   gives LLVM's sorted set).
4. Modules on other threads: multi-CGU builds and the allocator shim. The proof asserts one module, and handles are not
   retired at `LLVMContextDispose`, so a second context in one process could reuse addresses.
5. Out-parameters the recorder does not decode (`&mut *const c_char`, other `*mut &T` arrays), and callbacks.
6. Floating-point and non-C-convention text in trace answers (N10).
7. Over-uniquing and out-parameters **are** caught now (N1, N2).

## `// PORT:` decisions (for root to record)

1. **The generator is in `tools/llir/ffi_gen.ts`** (PORTING §6). Its outputs start `// GENERATED by tools/llir/ffi_gen.ts`. The
   implementation modules are listed in `src/rust_ts/llvm/impl_modules.ts`, so llir lanes do not edit `tools/`.
2. **Markers on the contract**: each export carries `// rustc: compiler/rustc_codegen_llvm/src/llvm/ffi.rs:<line> <name>`. Enums
   and bitflags carry a plain `// From …ffi.rs:<line> (enum X).` comment.
3. **The contract's types** (see "The contract's shape"):
   - every raw pointer is `| undefined`, and a null array with length 0 is ported as `[]`;
   - 64-bit integers are `bigint`;
   - `AllocKindFlags: u64` is a 32-bit `flags_companion` (its bits are below 2^6);
   - `LLVMGetValueName2` returns the name decoded from UTF-8 with its byte length: lossless for rustc's `&str` names (N13).
4. **The printer prints what the parser normalises**: floats in hex (`f0x…`), a non-C convention as `cc N`, and no annotation
   comments. The port-side trace's float `const` answers and `LLVMRustWriteValueToString` differ from LLVM's text for those
   (N10).
5. **No `Intrinsic::getAttributes`** on intrinsic declarations: the parser replaces them (plan-m7 §1b).
6. **Arguments are built eagerly** (LLVM builds them lazily; they are unnamed either way).
7. **RAUW of constants is in place** when the replacement is not already uniqued (`replaceOperandsInPlace`).
8. **`LLVMGetVersion` / `LLVMRustVersionMajor`** return 23.1.3, from `rustc -vV`, and the C API test checks it.
   `LLVMRustDebugMetadataVersion` returns 3 (`Metadata.h:54`).
9. **`LLVMRustSetNormalizedTarget`** accepts only the triples the C API test confirms are already normal.
10. **Data layout address spaces** (`P`, `G`) default to 0, and stop if the layout names them.
11. **`LLVMContextDispose`** does nothing (garbage collection).
12. **Null C strings follow the C++**: `StringRef` → empty, `Twine` → error.
13. **Replay applies `LLVMRustSetDataLayoutFromTargetMachine`'s effect directly** (a driver lane's stub). The proof asserts this
    is the only such effect.
