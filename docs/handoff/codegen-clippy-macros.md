# Handoff: codegen-clippy-macros (M8 wave 41, step 2; tools batch under `tools/codegen`)

Plan: `docs/plan-m8.md` D5 (first bullet), §2b–§2d, D4, D14, D18, D21. A new generator, `tools/codegen/clippy.ts`, expands
clippy's macros at the pin from the sparse checkout (`$RUST_TS_DATA/rust/src/tools/clippy`). Nothing is hand-ported.
**Counts agree with the plan: 835 lints, 51 early and 316 late sub-passes.**

**Oracle checks:** every generated value matches the oracle in both checks, with 0 mismatches:
- the expanded statics, passes and tables, against the oracle's own `-Zunpretty=expanded` of the real macro definitions;
- the lint table and the group table, against the oracle `clippy-driver -W help`.

Two parts are not emitted yet:
- **The combined passes** (`src/clippy_lints/lib.gen.ts`) are generated and oracle-checked, but are *pending*. The file imports
  the 360 hand modules that the contract lanes create, so it is written once they exist. It type-checks against stubs.
- **`define_Conf!`:** only its dispatch-free half is generated (below).

## §2d's tables (`src/clippy_lints/lint_tables.gen.ts`)

- **`SUB_PASSES`** has 369 rows: 2 pre-expansion, then the early and late fields in order. Each row gives:
  - `kind`, `field` and `ty`;
  - `declared_in`: the file of its lint-pass macro;
  - `lints`: `clippy::<name>` in lower case, in `lint_vec` order;
  - `files`: upstream paths, ready for `coverage.ts --missing`.
- **`LINT_GROUPS`** and **`LINT_GROUP_ALIASES`**: the groups `LintListBuilder::register` registers. Members are in
  `insert(declared_lints::LINTS)` order, which is the order `-W help` prints.
- **`UNOWNED_FILES`**: clippy_lints files in no pass. These are `lib.rs`, `declared_lints.rs`, `deprecated_lints.rs`,
  `combined_{early,late}_pass.rs` and `utils/mod.rs`.

**The rule for "implementing files"** (`subPassFiles`, plus the closure in `buildTables`). This is a `// PORT:` decision for
harness-m8d to know. A pass's files are:
1. the file of its lint-pass macro;
2. if that file is a directory module, every file under the directory except subtrees owned by another pass's directory
   module (when one `mod.rs` declares several passes, its shared files go to each of them);
3. any file with an `impl` of the pass type (`manual_let_else.rs` holds `impl QuestionMark`; a same-named type in another
   module counts only if the file names the pass's path);
4. transitively, every clippy_lints file a pass file names through `crate::…`. Naming only another module's lint static does
   not count: that static is generated, so nothing there needs porting.

This follows modules and `crate::` paths, not calls, so it can over-include (a file that only names a type). Over-including
delays a case's eligibility; it never makes a case eligible early. `super::super::` paths out of a pass's tree are not
followed (clippy_lints has no `super::super::` path). Seven passes pull in files from outside their own tree:
- AwaitHolding: `disallowed_types.rs`
- Matches: `collapsible_if.rs`
- Methods: `matches/manual_filter.rs`
- QuestionMark: `manual_let_else.rs`
- Unwrap: `methods/obfuscated_if_else.rs`
- DisallowedMacros: `utils/attr_collector.rs`
- ClonedRefToSliceRefs: `methods/mod.rs` and `matches/manual_filter.rs`

## Oracle checks (`bun tools/codegen/clippy-oracle.ts`)

**1. `-Zunpretty=expanded`** with the oracle rustc and its `rustc-dev`; nothing of clippy is built. The scratch tree is a copy of
the clippy sources in which every byte outside the expanded macro items is blanked, with newlines kept, so `line!()` is
unchanged. The scratch root is remapped to `/rustc/<commit>`, as in the oracle's own build (the clippy-driver binary's strings
show this path in `location`), so `file!()` is unchanged too.

It uses the real macro definitions:
- declare_clippy_lint's `lib.rs`, built to an rmeta (279 lines, the only thing compiled);
- `rustc_lint_defs`'s `declare_tool_lint!`, `declare_lint_pass!` and `impl_lint_pass!`, and `rustc_lint`'s
  `{early,late}_lint_methods!`, from the sysroot;
- clippy's `combined_*_pass.rs`, verbatim;
- `generate!`, `msrv_aliases!` and `define_Conf!` with `first_expr!` and `filtered_names!`.

The expansion reports resolution errors (the blanked types are missing) but prints in full; only macro output is compared. I
did not use `tools-deps`' cargo, because clippy_lints is not in that workspace and expanding through cargo would build its
dependencies; the blanked expansion needs no dependency.

## Pending: `src/clippy_lints/lib.gen.ts` (decision for root to record)

The expansion names the type of every sub-pass by module (`mod_utils_dump_hir.DumpHir`, D4's mirrored paths), plus `Conf`
(`clippy_config/lib.ts`), `FormatArgsStorage` (`clippy_utils/macros.ts`) and `AttrStorage` (`utils/attr_collector.ts`). None of
those hand modules exists yet, and the gate's `tsc` would fail on the imports. So the generator writes the file only once every
module in its `needs` list exists. Until then, the run prints `pending: … (N hand modules missing, first: …)`, and `--check`
(and the unit test) require the file to be absent.

**What clippy-contract-a / -b must do:** create the hand modules at D4's paths. Each pass type is a class that exports:
- `static new(..)` where upstream has `T::new(..)`;
- `static default()` where upstream has `T::default()` or `<T>::default()`;
- a zero-argument constructor where upstream uses a unit struct value;
- `static lint_vec()`.

`declare_lint_pass!` classes come from the `.lints.gen.ts` files; re-export them. An `impl_lint_pass!` type gets `lint_vec`
from `<T>_impl_lint_pass`, as in `src/rustc_lint/builtin.ts`. Then run `bun tools/codegen/clippy.ts` and commit `lib.gen.ts`.
After that it is an ordinary generated file. The contract lane needs no `tools/` edit; regenerating is not a generator change.

Generated forms (`// PORT:` decisions, in the generator):
- the ctor table above;
- `x.clone()` of the storages is `x`: both are `Arc` newtypes, so a clone shares the value;
- `new`'s parameter types come from the explicit `PARAM_TYPES` table, and an unknown type stops the generator;
- method parameter types are `Parameters<NonNullable<EarlyLintPass[K]>>[i]`, so they follow `passes.ts`'s interfaces;
- each field call is `{Early,Late}LintPass_provided.check_x(field, cx, ..)`, upstream's fully qualified trait call. The late
  pass guards each call with `!== undefined`, upstream's `if let Some(pass)`.

## Not generated: the rest of `define_Conf!` (follow-up batch)

`struct Conf`, `impl Default for Conf`, `Conf::get_metadata` (its `default` strings) and `Conf::deserialize` call
`<$ty as FromDefault<_>>` and `<$ty as DeserializeOrDefault<_>>`. Each call resolves to a different impl depending on the
field's type and the default's type:
- passthrough for primitives and `conf_enum!` types;
- `FromDefault<()>` for `Option`, `Vec` and `HashSet`;
- `FromDefault<&'static str>` for `String`;
- `FromDefault<&'static [U]>` for `Vec` and `HashSet`;
- the hand impls in types.rs, such as `SourceItemOrdering`.

Those impls are in de.rs and types.rs, which clippy-contract-b ports. Their TS names do not exist yet, so generating calls to
them now would mean inventing an API: a guess. I recommend a small follow-up tools batch, **`codegen-clippy-conf`**, after
clippy-contract-b's de.rs and types.rs lane. It would add the remaining expansion to `conf.gen.ts`, with that lane's impl names
as the targets. `parseConf` already parses every entry's `ty`, `default`, `default_text`, `rename`, `lints` and docs, and the
oracle check already expands `define_Conf!` in full, so the follow-up only adds emission and comparisons. Until then,
`conf.rs:122 default`, `:130 get_metadata` and `:146 deserialize` stay unported in coverage.

## Other `// PORT:` decisions

- **`<NAME>_INFO` is an untyped `Object.freeze({ .., category: "<Variant>" as const, .. })`.** The `LintInfo`/`LintCategory`
  types belong to declare_clippy_lint's hand module, which contract-a ports. With `LintCategory` as the usual string union
  (PORTING §5), the statics are assignable to it, and contract-a can type `declared_lints.ts`'s `LINTS` as `LintInfo[]`.
- **msrv consts are `Object.freeze(new RustcVersion(..))`**: shared constants (`RustcVersion` is `Copy`; `clone_RustcVersion`
  copies).
- **Name collisions.** clippy has an extra symbol named `Symbol`, so `sym.gen.ts` imports rustc_span as a namespace
  (`rustc_span_symbol`). misc.rs has a pass type named `LintPass`, so a module's imports are aliased (`rustc_lint_defs_<Name>`)
  when it declares the same name.
- **`ConfField`** is a string union with a companion const holding `NAMES`, `FIELDS`, `SUGG_NAMES` and the methods, plus
  `ConfField_discriminant` for `self as usize`. The generator refuses a variant that would collide with a companion member.
- The `rustc-lint:` marker of a lint is its name's line, as for rustc_lint. `location` uses the invocation's line, as `line!()`
  does.
