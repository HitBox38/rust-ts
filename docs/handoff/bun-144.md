### Design notes (`// PORT:`-like decisions)

- **Where the pin lives.** `GATE_BUN` is a TS constant in its own module, read by `gate.ts`, rather than a JSON file. It is
  typed, it needs no parsing, and a test ties it to `VALIDATED_BUN`. It is separate from `VALIDATED_BUN` because that list
  says which builds *can* make a subject binary, while `GATE_BUN` is the one build the gate *does* run on.
- **The check runs in every mode.** It also applies to source-mode gates, since the oracle keys, the unit tests and the
  static steps all depend on Bun.
- **What `accept` checks.** It compares the run's recorded `bun` with today's `GATE_BUN`. So an accept after a pin change
  refuses runs made on the old pin, which is the point. It does not check the Bun that `accept` itself runs on: `accept`
  only reads jsonl.
- **Older runs.** A gate.json without `bun` is let through with a `note:`. Every accepted run so far predates the field.
- **Test override.** `GateHost.bun` overrides the running build for tests only, in the same way `staticChecks` does. The
  CLI never sets it.

### 2.3 `optimize: { bytecode: false }` still takes effect

`Bun.build` builds are byte-for-byte deterministic on 1.4.4: two builds with the option gave the same sha1. That makes
the option's effect visible on the binary itself. All builds are `main.ts` with the builder's exact options, varying only
`optimize`:

| `optimize` | size (B) | sha1 |
|---|---|---|
| `{ bytecode: false }` (the builder's), two builds | 200,748,002 | `474edd44…`, both |
| absent (Bun's default) | 198,271,202 | `635b8be3…` |
| `{ bytecode: true }` | 198,271,202 | `635b8be3…` |
| `{ bytecodeRenamed: false }` (a misspelt key) | 198,271,202 | `635b8be3…` |

So 1.4.4 reads the key: the option changes the bytecode, and an unknown key is ignored silently, which is exactly the risk
F2 names. The depth row in §2.1 shows the effect at run time.

## 9. Review round 1 (docs/reviews/bun-144.md, REQUEST CHANGES): fixes

### F1: the Bun file the gate's children run is now checked from start to end

The gate process keeps its own build. Its children (static steps, the Bun-run oracles, source-mode subjects, the builder) run
the file at `process.execPath` as it is when each one starts. So a mid-gate upgrade went unnoticed, and `oracleVersion` could
store output from the new Bun under the old key.

The changes:
- `scripts/lib/bun-pin.ts` has a new reader, `readBunExe(path)`. It reads the file's content sha1 (not mtime: the file keeps
  the release's mtime) and what `<file> --revision` prints (`1.4.4+38afee6c8`).
- `execBunRefusal`: at the start, the file must be the running build (same version, and a revision that is a prefix of
  `Bun.revision`). Otherwise there is one `ERROR:` line, before any work: right after the `GATE_BUN` check, before the host
  reading and the run dir.
- `bunExeChange` re-reads the file before every suite and at the end; the static-stop path reads it too. On a change there is
  one `ERROR:` line naming where it was seen (`before suite X (during Y)`, `at the end (during Y)`). The suites left go to
  `notRun` with that reason, and the run fails. The line also says the last suite's cache entries may be under the old key.
  The gate does not try to purge them.
- gate.json `bunExec: { start, end, changed? }` is written in both writes.
- `accept` refuses a run whose `bunExec.start.sha1` and `end.sha1` differ (`acceptBunExeRefusal`). A gate.json without
  `bunExec` gets a `note:` only.
- A re-read costs one sha1 of the ~88 MB file plus one `--revision` spawn, about 0.1–0.2 s per suite.
- `GateHost.execPath` (tests only) replaces the path that is checked. The children still run `process.execPath`.

Tests, in `scripts/gate-bun.test.ts`, 15 in all (8 new):
- `readBunExe` on the running Bun, on a fake Bun (a script that prints `1.4.5+0123abcde`) and on a missing file.
- The start refusal by version and by revision.
- `bunExeChange` is by content.
- `acceptBunExeRefusal`.
- Real `gateRun` on two stub suites, with the checked file a symlink to the running Bun. A stub subject swaps it, with an
  atomic `rename`, for a symlink to the fake:
  - no swap: pass, start = end;
  - swap during the first suite: one `ERROR:` "changed before suite swap-b (during swap-a)", swap-b in `notRun`, `pass:
    false`, `bunExec.end` = 1.4.5;
  - swap during the last suite: seen "at the end";
  - the fake from the start: refused with 0 host reads and no run dir.
- `accept` with a changed, the same, and an absent `bunExec`.
