## 2. mbe `NamedMatches`
- `src/rustc_expand/mbe/macro_parser.ts`:
  - `MacroRulesIdentMap<V>` now wraps an `FxHashMap<number, [MacroRulesNormalizedIdent, V]>`.
  - Packed key: `name * 2^32 + ctxt`. It asserts `name < 2^21`.
  - `MacroRulesNormalizedIdent_key` hashes the key like `Ident::hash`: `write_u32(name)`, then `write_u32(ctxt)`. Its layout is 12 bytes, align 4.
  - `default(value: Layout)` now takes the value layout.
  - New `extend(other)`: std's `HashMap::extend`, which reserves from the exact size hint and then inserts in bucket order.
  - `iter()` walks the buckets in hashbrown order.
  - New `LAYOUT_NamedMatch`.
- `macro_check.ts`: `Binders` use `LAYOUT_BinderInfo`. Binders are never iterated, so their order cannot show.
- `macro_rules.ts`: `try_match_macro_attr` now calls `named_matches.extend(body_named_matches)`, like upstream.
- `transcribe.ts`: removed the `unported("std::collections::HashMap iteration order ... transcribe_sequence")` gate and the unused import.
- Audit of other Fx maps in rustc_expand and rustc_builtin_macros. None of these has an observable order, so none changed:
  - `macro_stats`: sorted by `print_macro_stats`.
  - `SuccessfulMatch` set: filtered and then sorted.
  - Lookup-only maps: `expanded_fragments`, `rebased_spans`, `FirstSets.first`, `fallback_cache`, asm `named_pos`.
  - Insert or contains only: format `explained`, `seen_type_names`, assert `paths`.
  - `FormatArguments::names` was already done by hashbrown-order.
- Oracle cases:
  - New `src/rustc_expand/mbe/mbe_b_oracle/cases/fxorder.rs`, with the fixture regenerated using the existing mbeprobe. The other 19 cases did not change. It covers:
    - the 5- and 15-name repeatable-metavariable lists (the 15-name map resizes);
    - `find_best_match_for_name` ties, for both repeatable and unrepeatable names;
    - the attr-rule `extend` path.
  - The oracle orders differ from insertion order, for example `$add, $asm, $alloc, $align, $abi`. mbe_b_oracle is 20/20.
  - format_oracle has 4 new cases: `named_many` (9 names), `named_captured_mix`, `named_width_mix` and `named_unused_many`. format.test.ts is 106/106.
- **Finding for root:** these cases use **predefined** symbols as metavariable names on purpose.
  - With fresh names (`$alpha`...) the oracle order differed from ours.
  - Cause: mbe_b_oracle.test.ts uses a stand-in `Session`. The probe runs a full `run_compiler`, which interns other symbols first, so fresh `Symbol` indices (and therefore the hashes) differ.
  - format_oracle goes through the ported `run_compiler`, and its fresh names (`alpha`..`iota`) match. That means the ported driver interns symbols the same way.
  - Any future Fx-order test that runs on a stand-in session must use predefined names, or replay the oracle's interning.

## 3. env_depinfo (investigation)
- Upstream type is `FxIndexSet<(Symbol, Option<Symbol>)>`. Here `Session.env_depinfo` is a `Set<string>` of JSON-encoded pairs.
- `env_var_os` and `write_out_deps` in passes.ts, and `track_env_var` in proc_macro_server.ts, already encode the pair's **strings**.
- `rustc_builtin_macros/env.ts` stored **Symbol numbers**, so `write_out_deps` would have printed `Symbol.intern(<number>)`. **env.ts was wrong and is fixed:** it now stores `[as_str(var), as_str(value) | null]`. passes.ts needs no change.
- This cannot be checked end to end yet, because the driver stops at `rustc_lint::late::unerased_lint_store` before dep-info is written.
- Oracle reference for a later driver case. Source: `#![no_core]` plus `#[rustc_builtin_macro]` env/option_env, with `const A: &str = env!("FXMAPS_A"); const B: &str = option_env!("FXMAPS_MISSING");`. Run with `FXMAPS_A=hello`, `--emit=dep-info`. The output ends with:
  `\n# env-dep:FXMAPS_A=hello\n# env-dep:FXMAPS_MISSING\n`

## PORT decisions
- Packed numeric key for `(Symbol, SyntaxContext)`. It is exact while `name < 2^21`, which is asserted.
- `LAYOUT_NamedMatch` = {24, 8} and `LAYOUT_BinderInfo` = {8, 4} are lower bounds, not exact `size_of` values: `NamedMatch` is pub(crate), so no probe can read its size.
  - On the oracle host (NEON, `Group::WIDTH` 8), hashbrown's placement depends on the pair size only through `size <= 1`. Any larger size therefore gives the same order. Both lower bounds are well above 1.
